An explicit `file:` AUTHORITY counts too, because `file://host/x.js` is an SMB fetch off the machine on Windows. How many separators open that authority was CHECKED in a real Chromium rather than read off the spec, because the answer is not "two or more": exactly two, or FOUR-or-more, give a host, while THREE is the empty host of an ordinary local path - so `file:////evil.example/x.js` really does fetch and a third-slash test alone called it local. Two host spellings that stay ON the machine are excluded WHATEVER the separator count, since reporting either would delete an author's local reference and make the gate reject a file with no egress at all: `localhost`, and a Windows DRIVE LETTER, which the file-host state turns into a path rather than a host (`file://C:/x`, `file://c|/x` and even `file://c:evil.example/x` are all the local file `file:///C:/...`, which is why the drive test does not require a separator after the colon). `localhost` is matched as the URL PARSER compares a file host rather than as a literal, because the parser percent-decodes the host and lowercases it through domain-to-ASCII BEFORE the file-host state turns the exact string `localhost` into the empty host: `file://local%68ost/x` parses to href `file:///x` in a real WHATWG parser, exactly like `file://localhost/x`, so a literal test reported a purely local reference as egress and both sides now spell the host one alternation per character with BOTH hex rows per letter (a `/i` regex folds `%6c` onto `%6C` but never onto `%4c`, and `%4c` decodes to `L`). The same percent-tolerance is right for the FOUR-or-more-separator arm, where the long run opens a real HOST to Chromium (the same deviation above) and a real Chromium was MEASURED percent-decoding that host before comparing, so `file:////local%68ost/x` parses to host `localhost` - the same excluded host the plain spelling reaches. Nothing that decodes to anything OTHER than `localhost` can match, so the widening cannot smuggle a host past either side: `%2F` and `%00` are forbidden host code points that fail to parse, and a host that merely STARTS with `localhost` is stopped by the terminator that follows. The rule the whole `file:` arm now keeps is CANONICALIZATION STABILITY: a value and the href the URL parser canonicalizes it to must get the SAME verdict, or a spelling hides an authority only the parser sees. Three shapes broke it, and none of them is reachable by a test that reads only the START of the value, because the parser's path state runs AFTER the host is emptied. (1) What the `localhost` exclusion may be FOLLOWED by is the end of the value, a `?` or `#`, or a SINGLE path slash - never two: `file://localhost//evil.example/x.js` empties the host and keeps `//evil.example/x.js` as the path, so the parser canonicalizes it to `file:////evil.example/x.js`, the four-separator UNC form this same arm rejects, and a bare `[/?#]` terminator blessed it as local on BOTH sides (the backslash spelling `file://localhost/\evil.example/x.js` reaches it too, through the cleanup that maps `\` onto `/`). (2) A DOUBLE-DOT segment pops the segment before it - including the very label an exclusion just matched - so `file:////localhost/../evil.example/x` and `file:////C:/../x.js` canonicalize onto the four-separator form with a different leading label; a `..` anywhere in the path therefore makes the arm match REGARDLESS of the `localhost` and drive-letter exclusions, in every spelling the parser treats as a double-dot segment (`..`, `.%2e`, `%2e.`, `%2e%2e`, case-insensitively). (3) An EMPTY path segment IS that four-separator form, and it arrives from values the separator arms never look at - `file:///.//x.js` and `file:/a/..//x.js` both canonicalize to `file:////x.js` from a three-slash or slash-less value - so it gets an arm of its own that ignores the leading separator count entirely, reading only a `//` in the PATH (a `//` after a `?` is in the query, which cannot change the path). A fuzz of 421,560 values against a real URL parser measured the result at this revision: ZERO remain where the predicate says local while the value's own canonical form is egress. The cost is over-detection in the safe direction, and it is pinned in the corpus rather than left implicit: `file://localhost//C:/x.js` (canonically the LOCAL `file:////C:/x.js`), `file://localhost/a/../b.js`, a bare `file://localhost//`, and an authored `file:///C:/a//b.png` are all now reported, while the controls beside them - `file://localhost/a/./b.js`, `file:///C:/local/x.js`, `file://localhost/x.js?q//h` - stay local. What the host spelling covers is PERCENT-ENCODING and CASE, which is the half of canonicalization a regex can model; the IDNA/UTS-46 half is an ACCEPTED, deliberate over-detection, so `file://<U+FF4C>ocalhost/x`, its percent-encoded UTF-8 `file://%EF%BD%8Cocalhost/x`, `file://LOCALHO<U+017F>T/x` and the soft-hyphen `file://local%C2%ADhost/x` all parse to href `file:///x` (measured) and are still reported. Percent-encoding does not reach the DRIVE-LETTER exclusion the way it reaches the host one, because that test reads the raw buffer the file-host state reads and `%3A`/`%7C` decode to forbidden host code points that fail to parse at all. The URL literal is recognized in the literal prefixes a browser resolves to a network host, and in the spellings that NORMALIZE into one of those before anything resolves them - by the URL parser, or by the JavaScript parser that produced the string. The prefixes are scheme plus slashes, protocol-relative (slashes only), and SCHEME-ONLY - a quoted `https:`/`http:` with NO slashes after it, which a browser resolves to the same host. On top of any of them the literal may carry the leading C0-or-space padding the URL parser strips (`" https://evil"`), an ASCII tab, LF or CR ANYWHERE inside the scheme or between the two authority slashes (`"ht<tab>tps://evil"`, `"/<tab>/evil"`), which the parser removes from its whole input and which an ordinary string literal can carry as a real character, a BACKSLASH in place of either authority slash - four source backslashes (`"\\\\evil"`), since a literal spends two per runtime backslash, or an escaped slash (`"\//evil"`) - which for a special scheme the parser treats exactly like a slash, a JavaScript LineContinuation - a backslash followed by a line terminator - which evaluates to NOTHING in an ordinary and a template literal alike, and an ESCAPING BACKSLASH before any literal element (`"\https://evil"`, `"htt\ps:evil"`, `"https\://evil"`), because a backslash before a character that begins no escape sequence is a NonEscapeCharacter and evaluates to that character - the cheapest spelling of the lot, one keystroke and no decoder, and the one that would otherwise have defeated every other shape at once. The padding stops one code point short of the class the network-URL predicates allow: U+0000 is deliberately EXCLUDED, because the HTML parser replaces a NUL in script data with U+FFFD (which the URL parser does not strip), so a NUL-padded literal can never navigate and matching it would only make the validator, which reads the RAW text, reject a document the exporter - which reads the PARSED text - preserves. None of these needs aliasing, computed access or runtime assembly - just the URL spelled with one extra character - and while the check insisted on the exact raw spelling the whole channel was open to a one-token change and the strict validator agreed with the strip and blessed the file too. The authority branch deliberately does NOT require a host character after the two slashes: a sink assigned a quoted protocol-relative prefix concatenated with a host assembles a real beacon and the check fails CLOSED on it, at the price of also removing a host-less `"//"` or `"/\"` reference a browser would resolve locally - the same over-match direction this row already owns, and the reason a future reader must not "tighten" it by demanding a host. Backslash PARITY is load-bearing and is pinned by its own controls: a literal spends TWO source backslashes per runtime one, so THREE source backslashes leave a single runtime backslash and a local path where FOUR leave the two an authority needs, and an EVEN run before a scheme is a real backslash the browser resolves locally rather than an escaping one - which is why the branch is spelled `(?:\\?\/|\\\\)` rather than a naive `[\\/]{2}`, and why the escaping-backslash tolerance is a single optional `\\?` rather than a run. (The attribute-side network-URL predicates now agree about a backslash authority - they normalize the value the way the URL parser does before testing it - so the remaining divergence is narrower and deliberate: this check also recognizes a SCHEME-ONLY spelling, which the attribute predicates still require the two slashes for, because widening those alone would make the gate reject a file the exporter just produced. #961 moves that pair together; do not "reconcile" it by loosening this one.) Every added run is separated from its neighbour by a mandatory literal element, and each run's own two alternatives are told apart by their SECOND character (the line-terminator branch keeps only U+2028 and U+2029, because a backslash before LF or CR already falls inside the class beside it), so no input has two parses of a run. The two AUTHORITY alternatives can both begin with a backslash, but both are fixed-width, so choosing between them costs a bounded retry rather than a split of the input: the tail cannot backtrack superlinearly. Recognition is a LINEAR SCAN driven from the `location`/`open` anchors rather than one pattern: the earlier pattern carried the prefix chain as an unbounded repetition in front of the sink, so it re-entered that chain at every position a prefix could follow and a long NEAR-match cost QUADRATIC time (`window . ` repeated measured 2.3s at 18 KB and 174s at 144 KB, 4x the time for 2x the input). That was cheap to trigger, because the same predicate also runs over the vendored payload's INFLATED bytes, where a few hundred base64 bytes buy megabytes of near-match; the damage is bounded to an Export Offline that appears to hang, but an export that appears to hang is indistinguishable from a broken feature. The scan recognizes exactly the shapes the pattern did, pinned against it in BOTH directions, and its SCALING is pinned at 10x steps rather than at one fixed size, which is why the quadratic term survived the earlier backtracking guard. Linearity is a property of the WHOLE predicate, not just the sink search: the LOCAL-BINDING regex that decides whether the script declares its own `location` is the other full-text pass, and it carried the same class of defect one level down - its `function` alternative joined two unbounded whitespace runs around an OPTIONAL identifier (`function WS* IDENT{0,100} WS* \\(`), so a run never followed by an identifier was split every possible way and each split re-ran the bounded `[^)]{0,400}location` search, costing QUADRATIC time in the RUN's length (0.13s at 5 KB, 22.5s at 80 KB through the public predicate). The optional identifier and its own trailing run are bound inside one group now, so a run has a single parse and a failing split costs nothing; the recognized language is unchanged, since the old spelling with zero identifier characters is the new group skipped. Its scaling therefore grows the RUN rather than a repeat count, because a fixed gap repeated n times stays linear and hides exactly this term. The strict validator runs the same scan, with every shared literal BYTE-IDENTICAL and the walk that joins them pinned by evaluating the exporter's own source in node, so a hand-authored offline file with that shape is not blessed as offline-clean either; every metacharacter whose meaning differs between the JS and Python engines is spelled out rather than shared, because `\w` is ASCII-only in JS but Unicode-aware in Python and U+FEFF is JS whitespace but not Python's, which made the two copies disagree on real inputs. The IDENTIFIER-BOUNDARY class inside that scan is spelled as the COMPLEMENT of the boundary characters for the same cross-engine reason: a JavaScript identifier is not ASCII, so an ASCII-only class read every non-ASCII identifier character as a BOUNDARY, and a purely local binding whose name merely ENDS in `location` behind one (`<non-ASCII letter>location.href = <url>`, which navigates nothing) was deleted whole by the export and REJECTED by `--strict` - the false-positive direction that silently destroys an author's content, and the one this check is meant to avoid above all. It cannot be fixed by reaching for `\w` (ASCII-only in JS, Unicode-aware in Python) and Python's `re` has no Unicode property escape, so the class lists every ASCII character that cannot appear in an identifier EXCEPT `.`, plus the exact whitespace set the scan already uses, and reads everything else as an identifier character. The `.` exception predates this spelling and is load-bearing rather than an oversight: a member-expression dot must CONTINUE the chain, so `cfg.location.href = <url>` reads as some other object's `location` and stays benign, and making it a boundary would delete that script. That settles the ASTRAL case in both engines at once rather than needing a second rule: a supplementary code point is a surrogate PAIR to `charAt` and a single code point to Python, and neither reading is in the boundary list. That rule is one instance of the UNIT MODEL this pair now commits to, recorded here rather than left implicit in two languages whose string indices count different things. The model is NOT that the two copies count nothing - they do count - but that every length or index comparison in the pair is unit-INSENSITIVE, so a JavaScript index (UTF-16 code units) and a Python index (Unicode code points) cannot reach different verdicts on the same input. What is FORBIDDEN is the one shape that is not: an engine-native count BOUNDING a span of arbitrary source text, however it is spelled - the distance between two source positions, the width of a slice, a bounded regex quantifier, or an explicit counter. Replacing the window with a tokenizer removed that shape rather than moving it. The comparisons that DO survive fall into five CLASSES rather than a list of sites - stated as classes deliberately, because a site list goes stale the moment a helper is renamed and a class an author can test their new line against does not. (a) An advance or width over an ASCII token the code just matched - the anchor match width that selects the sink arm (`m[0].length === 4` against `after - at == 4`), the anchor restart, every `startsWith`-then-advance (`//`, `/*`, `*/`, the HTML comment opener, `${`, `=>`, `++`, `--`, `...`), and the `pos >= len(name)` guard - is safe because the token is ASCII, so its width is the same number in either model. (b) The single-token peek after a declaration keyword (`_offlineShadowDeclStarts` / `_offline_shadow_decl_starts`, `after.length === 1` against `len(after) == 1`) is safe ONLY because each engine's peek is exactly one unit OF THAT ENGINE - a lone surrogate to `charAt`, a whole code point to Python - and both classify as an identifier character. This is the one class that is merely unit-INSENSITIVE rather than unit-IMMUNE, so it is the one a well-meaning edit can break: making the JS peek astral-aware (`String.fromCodePoint`) without mirroring the Python side re-opens #1112 at this exact site, and any change to `_offlineShadowIdentChar` on one side must be mirrored on the other. (d) The backwards prefix tail (`OFFLINE_NAV_PREFIX_MAX`) is safe because the slice is only ever tested with `endswith` against ASCII prefix names, so a code-unit slice and a code-point slice end in the same characters. (e) A comparison that ORDERS two positions in the same string, or tests one against that string's length (every loop bound, and the regex-versus-division position test), is invariant because both operands live in one index space, whichever one it is. Note the sharp edge on (e): ordering and equality are invariant, SUBTRACTION is not - `a > b` answers the same in both models where `a - b > 400` does not, and that subtraction is precisely the forbidden shape above rather than an instance of this class, so (e) never licenses measuring a distance. Classes (a), (c), (d) and (e) are unit-IMMUNE - respelling any of them in code points changes no verdict on any input - which is why the corpus that pins this has real GUARDS only for (b) and carries the others as illustrations that the shapes are reached and agreed on. If a bound over arbitrary source text is ever genuinely needed again it is spelled in UTF-16 CODE UNITS - what the exporter, and therefore the shipped document, actually runs - and mirrored EXPLICITLY on the Python side, which must then count units rather than characters, instead of being assumed.
