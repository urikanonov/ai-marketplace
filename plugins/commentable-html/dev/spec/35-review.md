| CMH-REVIEW-16 | The `reviewedSections` block is resolved by the EMBEDDED COMMENTS region that OWNS it - the region's own BEGIN/END comment markers plus document order - among the blocks the CONTENT-ROOT BOUNDARY accepts (CMH-EXP-17), not by the first `getElementById` match, on BOTH the load and the export path, and only a `<script>` can carry it (exactly what the validator's shape check accepts, so the two cannot disagree about what the block is). A decoy block carrying the same id elsewhere is ignored on load and left with its own contents on export, while the region-owned block keeps taking the state; a document that owns no such block (an older file) still gets a fresh one inserted after its region-owned `embeddedComments` block. Resolution is deliberately conservative: markers that are ABSENT still let a LONE block resolve (a file upgraded from before the feature existed keeps working) - safe only because the boundary already dropped every candidate inside the content root, so an authored decoy can never BE that lone block, and a CONTESTED content root drops them all and resolves nothing, MALFORMED markers (not exactly one ordered pair document-wide, which is also a validator error, so a stray authored comment that quotes a marker line disables review rather than corrupting it) resolve nothing, and `<noscript>` contents are skipped on both paths because `DOMParser` (scripting disabled) parses them as real nodes while the live document does not - so the export can never write into a block the reader's browser treats as text. When nothing can be attributed to the region the export declines - it neither overwrites the decoy nor invents a third block, and it also declines to anchor a new block when more than one `embeddedComments` block the layer OWNS exists (a decoy inside the content root is not one of them, so it cannot veto the insert), since the comments themselves are written into the first one - and the reason travels back to the caller so the single download toast carries it, naming the ONE state it hit (every block inside the content root, a contested content root, several owned blocks, malformed markers, or a block outside the region) rather than listing every possible cause (a separate toast would be replaced by it); | CMH-REVIEW-17 | Section hashes are taken over the CANONICAL (authored source-order) content, exactly like the whole-document hash, so a reader's persisted table sort can neither flip an already-reviewed section to "changed" nor store a sorted-order hash when a section is marked reviewed while a table is sorted (which would then flip when the sort is cleared). The canonical order is READ, never restored by moving live rows: `_cmhScanSections()` walks the content root itself and, while a sort is active, visits a `<tbody>`'s rows in stamped `data-cmh-row` order permuted through their existing slots (so the authored inter-row whitespace still counts exactly once), leaving the DOM untouched. That matters because the scan runs on every sidebar/badge refresh: mutating the rows there would blur a focused control, collapse a live text selection mid-comment, and churn the table-scroll and widget observers. The runtime OWNS that index - `_indexTableRows()` re-stamps every sortable row with its position in the FILE before any persisted sort is applied - and only a body whose rows all carry the stamp is reordered, so an authored or stale `data-cmh-row` cannot silently re-order a table away from the source the Python hasher reads. | `tests/90-section-review.spec.js` - `a persisted table sort does not flip a reviewed section to changed (CMH-REVIEW-17)`, `computing review state never reorders the reader's rows or steals focus (CMH-REVIEW-17)`; source: `assets/js/84-section-review.js` - `_cmhScanSections()`, `_cmhCanonicalChildNodes()`, `computeSectionStates()` |
