| CMH-THREAD-09 | An in-progress inline reply/edit draft (a reply, a reply edit, or a root-note edit) is preserved across a sidebar re-render (comment sort, a note-typing debounce, a checklist change, etc.) - the editor is re-opened with the same text rather than silently dropped - and still saves normally afterward. The reviewer's SELECTION is part of that draft: the re-opened editor restores the snapshotted `selectionStart`/`selectionEnd` instead of collapsing the caret to the end, so a re-render between selecting a word and clicking a formatting-toolbar button still wraps the word rather than appending bare markers. FOCUS is not: the snapshot records whether the editor owned focus (a deferred focus the open path has queued but not yet delivered counts as ownership), and the re-opened editor is only re-focused when it did, so a re-render triggered from elsewhere (a note the reviewer is typing into, a checklist tick, the Sort button) restores the text and selection without pulling the caret out of the control actually in use. When focus was on the editor's own formatting toolbar or its Save/Cancel button - an element the re-render destroys - it is handed back to the rebuilt equivalent control rather than dropped into the textarea. An open MODAL dialog (Manage storage, the clear-all confirm, Help) vetoes that ownership outright for the whole rebuild: the side pane sits BEHIND the dialog's overlay, so the re-opened editor keeps its text and selection but is never focused - focus there would escape the ``aria-modal`` dialog's trap into a control the reviewer can neither see nor reach - the veto is enforced at DELIVERY time too (the deferred focus timer, the post-save hand-back, and an editor's close-restore all stand down while a dialog is up), so a focus armed before the dialog opened cannot land behind it either; and focus that is not inside the dialog - stranded on ``<body>`` by the rebuild, or moved out into the document by a delete run FROM the dialog - is handed back to it, preferring the dialog's own declared safe default (``.cm-modal-default``/``[autofocus]``) over raw DOM order so a destructive confirm button is never made the Enter-default, and skipping any candidate that cannot actually take focus. Focus the reviewer genuinely holds inside the dialog (or on a toast, which sits above the overlay) is left alone. Re-clicking the edit action on an editor that is already open only re-focuses it, keeping the live selection and its anchor direction. | `tests/92-threads.spec.js` - `an in-progress inline reply draft survives a re-render such as sorting (CMH-THREAD-09)`, `an in-progress ROOT edit draft survives a re-render (CMH-THREAD-09)`, `a re-render preserves the draft's SELECTION, so the formatting toolbar still wraps it (CMH-THREAD-09)`, `a re-render triggered from elsewhere leaves focus where the reviewer put it (CMH-THREAD-09)`; `tests/72-storage.spec.js` - `deleting a comment from the manager keeps focus in the dialog with an inline draft open (CMH-THREAD-09)`, `a re-render while a modal is up never hands focus to the pane behind it (CMH-THREAD-09)`, `a re-render while a modal is up leaves focus on the dialog control the reviewer is using (CMH-THREAD-09)`, `a deferred editor focus armed before a modal opens is not delivered behind it (CMH-THREAD-09)`, `a stranded focus is handed to the confirm dialog's SAFE default, not its danger button (CMH-THREAD-09)`, `focus parked in the document behind an open dialog is pulled back into it (CMH-THREAD-09)` |

| CMH-THREAD-11 | Focus survives a re-render of the comment list. `renderComments()` replaces the whole list, so a control the reviewer is on - the checklist, note, and board change cards' `reset` buttons, and the comment (`del`) and reply (`reply-del`) delete confirms - is destroyed by the very render it triggered, and the reviewer used to be dropped on `<body>` with no way back but tabbing in from the top of the page. EVERY render notes where focus was before it rebuilds and hands it back afterwards, so this holds however the render is reached - synchronously from the click, a frame later through the board's mutation observer, or twice over when two renders are queued - rather than depending on each handler to remember. Focus goes to the equivalent rebuilt control (matched by the owning reply entry or card's identity plus the same `data-act`); else to whichever control took its index in the rebuilt list and then outwards from there, so a candidate that still refuses focus hands off to its neighbour rather than to the top of a long list; and finally to the list container itself (`#commentList`, `role="region"` + `aria-label="Comments list"`, `tabindex="-1"`, carrying its own inset focus ring), so an emptied list still lands the reviewer on the panel rather than on `<body>`. A candidate that cannot actually take focus is skipped rather than silently swallowing the restore, since `focus()` is a no-op on a hidden, disabled, or inert element and the comment filter hides non-matching cards outright; the index is taken over that same filtered sequence, so cards the filter hides cannot shift it and push the restore onto a distant control. Only focus that was INSIDE the list is carried: a render triggered from outside it (a note being typed, a checklist ticked in the document, the Sort button) leaves the caret exactly where it is, an inline editor's focus is carried by its own draft snapshot instead (CMH-THREAD-09, including a deferred focus that snapshot has queued, and the save paths that focus their own rebuilt control), and a rebuild that stranded nobody changes nothing.
