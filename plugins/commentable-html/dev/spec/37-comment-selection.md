## Per-comment selection: Copy selected and Delete selected comments

| Feature id | Behavior | Covering tests |
| --- | --- | --- |
| CMH-PICK-01 | Every side-pane comment card carries an obvious `Select` control in its meta row - a real `<input type="checkbox">` inside its label, so it is keyboard-operable and announced as a checkbox for free, with an `aria-label` naming the comment it picks (`Select comment #N`). Checking it selects that comment THREAD (a picked root carries its replies with it, CMH-THREAD-02/03) and gives the card an accent `cm-card-picked` ring so a selection is legible while scanning the list; unchecking gives it back. Only thread ROOTS are pickable - a reply has no pick control of its own that could put half a thread in the selection. Toggling never re-renders the list, so an inline reply/edit draft open in another card keeps its live DOM node and its text. | `tests/99-comment-selection.spec.js` - `every comment card carries a Select control that picks that thread (CMH-PICK-01)`, `picking and clearing never re-render the list, so an open draft survives (CMH-PICK-01, CMH-PICK-05)`; `tests/72-followups.spec.js` - `the side pane search row, dropdown menu items and card edit action are >=44px touch targets on mobile (CMH-RESP-15)` |
| CMH-PICK-02 | While at least one comment is selected, BOTH copy controls (the sidebar `#btnCopyAll` primary and the floating toolbar's `#btnCopyAllTop`) relabel to `Copy selected` and take a tooltip naming the COUNT (`the 2 selected comments`), so a reviewer working from the COLLAPSED toolbar - who sees the relabelled button but not the panel's selection bar - can still tell what is picked. A selection bar appears under the panel's primary row announcing the live count (`N comments selected`, `aria-live="polite"`), and because that live region is refreshed after EVERY render (a sort, a checklist tick, a note keystroke) it is written only when the text actually CHANGES, so an unchanged count is never re-announced while the reviewer is doing something else. With no selection the controls read `Copy all` and the bar is hidden, so the all-or-nothing default is unchanged. | `tests/99-comment-selection.spec.js` - `a selection relabels the copy control to Copy selected and counts itself (CMH-PICK-02)`, `the live count is written only when it actually changes (CMH-PICK-02)` |
| CMH-PICK-03 | `Copy selected` emits ONLY the selected threads - each picked root followed by its replies - in the Markdown body, in the `# ... review (N comments)` heading count, and in the machine trailer's `HANDLED_IDS_JSON` array, so the agent can never mark a comment the reviewer did not hand back as handled and prune it out from under them. Unselected comments appear nowhere in the bundle. | `tests/99-comment-selection.spec.js` - `Copy selected emits only the selected threads, replies included (CMH-PICK-03)` |
| CMH-PICK-04 | A partial hand-back declares itself: the bundle carries a `Scope: selected comments only (N of M open comment threads)` line right after `Source:`, so the agent never reads a missing comment as already handled. A selection is a COMMENT-only scope - the tracked widget-layout, checklist, and editable-note change sections are omitted and their machine-trailer state stays canonical `{}`, because those changes are not selectable and must not ride along on a partial hand-back. Because that canonical `{}` cannot say "withheld" apart from "nothing pending", a further `Withheld:` line names the tracked change KINDS that DO exist and were held back - and it appears only when such changes genuinely exist, so it never becomes noise the agent learns to skip. With no selection the same document still hands every tracked change back exactly as before, with neither line. | `tests/99-comment-selection.spec.js` - `a partial hand-back declares its scope and carries no tracked note change (CMH-PICK-04)`, `a partial hand-back with nothing withheld says so by staying silent (CMH-PICK-04)` |
| CMH-PICK-05 | The selection bar carries a `Clear selection` button that deselects every picked comment and DELETES nothing - the cards, the store, and the copy control all return to the no-selection default. It resets the rendered checkboxes in place rather than re-rendering, so an open inline draft keeps its live DOM node and its text. When that button HELD focus, clearing hands focus to a still-visible control first (`Copy all`) rather than dropping it on `<body>`, because clearing hides the bar the button lives in and `.cm-skip [hidden]` removes it from layout - the same contract every other vanishing control in this panel keeps (CMH-THREAD-11). The floating toolbar's overflow menu carries the same item (`#btnClearSelectionTop`, hidden until a selection exists, sitting between `Save as PDF` and `Manage storage` so the data-management pair stays adjacent per CMH-UI-13), because with the panel collapsed that menu is the only chrome a reviewer has and a `Copy selected` button they can neither inspect nor undo is a dead end; it restores focus to the menu's own trigger, exactly like `Delete all comments`. | `tests/99-comment-selection.spec.js` - `Clear selection deselects everything and deletes nothing (CMH-PICK-05)`, `Clear selection hands focus to a still-visible control (CMH-PICK-05)`, `the collapsed toolbar can inspect and clear a selection too (CMH-PICK-05)`, `picking and clearing never re-render the list, so an open draft survives (CMH-PICK-01, CMH-PICK-05)` |
| CMH-PICK-06 | The sidebar `More` menu grows a `Delete selected comments` item that is HIDDEN unless a selection exists. Activating it confirms first through the same `showConfirm` dialog Delete all uses (naming the comments AND the replies that go with them, cancel-by-default, Escape cancels), then deletes only the selected threads - root and replies together - tombstoning every id so the whole thread stays deleted across a reload, closing any editor or dialog left showing a removed id, dropping the highlights, and saving, while every unselected comment is left intact. Focus returns to the still-visible `More` trigger. | `tests/99-comment-selection.spec.js` - `Delete selected comments shows only with a selection and deletes only those (CMH-PICK-06)`; `tests/72-followups.spec.js` - `the side pane search row, dropdown menu items and card edit action are >=44px touch targets on mobile (CMH-RESP-15)`, `enlarging the side pane's controls does not starve the comment list on a landscape phone (CMH-RESP-14)` |
| CMH-PICK-07 | The selection is TRANSIENT: it lives only in memory, so picking changes not one byte of `localStorage`, and it is never embedded in an export - a file exported WHILE a selection is live carries the selection chrome hidden, no `cm-card-picked` card, and no per-comment selection flag, so a recipient (or a reload, or a second tab) starts from the all-or-nothing default rather than inheriting the sender's view. It is also self-pruning - resolved against the live thread roots on every read - so a selected comment deleted from its own card, from the in-document dialog, or by Delete all comments simply leaves the selection, and the copy control falls back to `Copy all` once nothing is left picked. | `tests/99-comment-selection.spec.js` - `the selection is transient and prunes a deleted comment (CMH-PICK-07)`, `a selection never travels inside an export (CMH-PICK-07)` |
| CMH-PICK-08 | A comment card ships ONE definition of "an action": `jump`, `edit` and `delete` sit on the SAME row as `Reply` (`.cm-card-acts`) and share its look and feel - the same `cm-card-btn` bordered pill, border, radius, font and padding - instead of the previous split between small plain text buttons on the meta line and an accent pill a row below, and none of the three is left behind on the meta line. `delete` is pushed to the row's end so the destructive action stays clear of `Reply` (CMH-RESP-14), and every one of them keeps the >=44px phone touch target on both axes (CMH-RESP-07/CMH-RESP-15). Opening the inline reply editor stands the WHOLE action group down for the duration, so the composer owns the row and no action is usable beside it; cancelling gives the row back. | `tests/99-comment-selection.spec.js` - `jump, edit and delete share the Reply row and its look and feel (CMH-PICK-08)`; `tests/72-followups.spec.js` - `the side pane Reply button and identity Save/Cancel are >=44px touch targets on mobile (CMH-RESP-14)`, `sidebar comment-card action buttons are >=44px tall on mobile (CMH-RESP-07)` |
| CMH-PICK-09 | The comment search hides non-matching cards outright, so a pick can be selected but off screen while `Delete selected comments` would still delete it. Both the selection bar and the confirm dialog disclose that: the bar's count gains `(N hidden by search)` and the dialog adds `N of them is/are hidden by the current search`, so a filtered list can never imply the selection was narrowed with it. The disclosure disappears again the moment the filter is cleared. The bar is a THIRD transient header row on top of the search and identity ones, so on a short landscape phone it keeps the comment list a usable scroll window and its `Clear selection` button follows the search row's viewport-HEIGHT target gate (the WCAG 2.5.8 AA 24px floor below 360px, the full 44px above it, per CMH-RESP-16), while every reachable `More` item - the selection-revealed one included - still scrolls fully into the menu. | `tests/99-comment-selection.spec.js` - `a pick the comment search hides is disclosed before it is deleted (CMH-PICK-09)`, `the selection bar and its menu item stay usable on a landscape phone (CMH-PICK-09)` |
