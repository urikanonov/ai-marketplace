| CMH-BUILD-17 | Element-clipped tutorial screenshots are DIMENSION-STABLE across renderers. Their clip height is derived from the element's laid-out height, which depends on FONT METRICS, not on the browser. The capture does not use the report's own font stack: `freezeMotion` pins it to `font-family: Arial, sans-serif !important`, and that pin is only as shareable as Arial is - Windows resolves real Arial, while the pinned Linux container ships no Arial at all and fontconfig substitutes Liberation Sans, which is metric-compatible with Arial in ADVANCE WIDTHS (so the width is identical to the pixel and no shot drifts horizontally) but not in VERTICAL metrics. Issue #698 measured `.cmh-checklist` under identical CSS (`font-size: 15px`, `line-height: 23.25px`) and an identical lockfile-pinned chromium: each row renders 23.391 CSS px tall on Linux versus 23.250 on Windows, so the element measures 230 CSS px instead of 228, which at `deviceScaleFactor: 2` is a 4 device px PNG delta with no content change. `tools/shot_clip.mjs` is the single source of that geometry (`CLIP_QUANTUM`, `DEVICE_SCALE`, `DIMENSION_DELTA_PX`, `MAX_WIDTH_DELTA`, `quantizeClipHeight()`, `clampedClipHeight()`, `heightDeltaAllowed()`), and every CONTENT-derived clip height in `capture_tutorial.mjs` - the element clip, the fixed-region clip, and the comment-search clip - is snapped onto that grid, so the drift collapses onto one value and the PNG dimensions stop depending on which renderer produced them (verified: the same checklist scene renders 2444x464 on a Windows host and in the pinned container). A clip bounded by the viewport or by a panel is quantized LAST and DOWNWARD (`clampedClipHeight`), so a clamped clip lands on the grid too; quantizing up and then clamping would leave an off-grid height, and an element that clamps on one renderer but not the other would differ by an arbitrary sub-quantum amount - the same bug moved rather than fixed. Only the height is quantized, because the layout width comes from the fixed viewport; full-viewport clips are a fixed 1320x900 box and are left alone. The guarantee holds while the per-shot renderer drift stays under one quantum (about 0.6% of a clip height for the measured font pair, so ~5.4 px at the 900 px viewport ceiling); a wider gap moves two quanta and fails loudly, which is the signal to raise the quantum rather than widen the budget. None of it introduces gate/strip drift, and the two now agree in BOTH directions rather than the gate merely staying looser: offline mode rejects EVERY `meta[http-equiv=refresh]`, exactly as the export removes every one whatever its URL (CMH-OFFLINE-05 records why that direction was chosen over the exporter keeping a relative one), and this target parser decides only WHICH message the rejection carries. A `javascript:` or `data:` target is therefore still not reported as network egress - mainstream engines refuse both as refresh targets - but the meta itself is rejected like any other. The NEIGHBOURING CSS network-literal gates - `CSS_NETWORK_URL_RE` and `CSS_NETWORK_IMPORT_RE`, the `@import` scan - now read the same widened shape (#961), and so does `NETWORK_URL_RE`, the ATTRIBUTE predicate the `_link_loads` path and every media/form/background check feed, whose parser-faithful input cleanup and `file:` authority arm landed earlier with #923. All three CONSUME the run of slashes after a special scheme rather than requiring two, because the special-authority states ignore that run, so `url(https:host/x.png)`, `@import "https:host/t.css"` and `src="https:host/x.js"` are caught as the network loads a browser resolves them to; and all three require a non-empty HOST, so an authority terminated at once - `url(https://)`, `url(//)`, a bare `https:` - stays local rather than being reported as a beacon it cannot be (which also closed a small pre-existing drift, where the CSS gate reported `url(//)` and the strip left it alone). (a) EXCLUSIVITY was enforced only for the directives whose required token is `'none'`. | CMH-VAL-22 | Every implementation that locates a region marker IN TEXT answers one canonical corpus identically. The rule lives in four places that cannot share a helper - the runtime (`_cmhRegionMarkerMatches`, inlined into every document), the validator package, the shipped authoring tools and the maintainer-only build tool are separate distributions - so `tests/fixtures/region_marker_parity.json` is the contract instead: `tests/test_region_marker_parity.py` pins the three Python copies and `tests/59-region-marker-parity.spec.js` pins the runtime, over the same cases (inline `<!-- -->` and `/* */` forms, a bare marker line inside a block comment, `=` decoration, tab padding, CRLF, prose that is not a marker, a name carrying regex metacharacters, and one case per separator below). A LINE breaks on `\n` ONLY, the way the runtime's raw-text scan sees it: Python's `str.splitlines()` also breaks on `\x0b`, `\x0c`, `\x1c`, `\x1d`, `\x1e`, `\x85`, `\u2028` and `\u2029`, and treats a lone `\r` as a terminator, so a marker "line" that exists only after one of those splits used to be COUNTED by the validator, the build and the upgrade tool while the runtime that reads the file back ignored it - two views disagreeing about which comment IS the boundary, the same class of defect the count views were aligned on in CMH-VAL-20/21. The three Python copies also expose the same `_MarkerMatch.start(group)` / `end(group)` signature, and REFUSE any group but 0 or 1 (which are deliberately the same span) rather than answering a wrong one, so a caller written against `re.Match` fails loudly. Two bounds are recorded rather than papered over.
