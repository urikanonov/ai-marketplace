# multi-duck feature specification

The `multi-duck` skill convenes a panel of independent rubber-duck reviewer subagents (each on a
different model) over the work in flight, consolidates their findings, and autonomously applies the
safe fixes. It ships as a single documentation skill (`pkg/skills/multi-duck/SKILL.md`) with no
runtime code, and it targets both Claude Code and the GitHub Copilot CLI.

Because the shipped surface is an instruction document, its "features" are the promises the SKILL.md
makes and the plugin's registration and dual-host packaging. Each is pinned by a covering test that
runs in the required `validate` and `cross-platform` CI jobs (they run
`python scripts/run_script_tests.py`, which discovers `scripts/test_*.py`). The plugin has no browser
runtime, so its
tests are Python, not Playwright; the site page for the plugin is covered separately by the
`SITE-MDUCK-*` rows in `site/tests/SPEC.md`.

Coverage notation: each row names the covering test method in `scripts/test_multi_duck.py`.

| MDUCK-SCOPE-12 | The panel respects a project's DECLARED threat model instead of rediscovering its non-goals every run. Bundle assembly collects the repo's written threat model, trust boundaries, and accepted residual risks (a security spec, an "accepted risk" / "non-goal" / "out of scope" section, or a row declaring a control to be defense-in-depth behind a stronger layer) READ FROM THE BASE/TARGET REVISION rather than the reviewed checkout - otherwise a change could add a non-goal declaring its own vulnerability class accepted and have the panel suppress findings about itself, from a diff that is untrusted data; a proposed threat-model edit is instead reviewed as a subject in its own right - into `context.md`, alongside the list that stays in scope REGARDLESS - a change that weakens a declared enforcement layer, a false positive that breaks or rejects benign input, and drift that makes a tool emit output its own validator rejects. Every duck's hard rules then forbid reporting a finding whose attacker the project declares TRUSTED, whose effect a named enforcement layer already blocks unconditionally, which is one more INSTANCE of an already-accepted residual, or which is a PRE-EXISTING defect noticed incidentally (equally present on the base revision) rather than a property of the change under review - that last class alone was 47% of the issues filed here in one two-day window and is what held the branching factor at 1.52, above the 1.0 at which a backlog stops growing; the narrow exception is user-observable breakage, data loss, or a security issue reachable under the declared threat model; a duck that disagrees with a non-goal raises it once under `QUESTIONS:` rather than laundering it into `FINDINGS:`. Three safeguards keep that gate from becoming a suppression tool. (a) A reproducible FACTUAL DISPROOF of a stated enforcement claim is always a FINDING and can never be dismissed by citing the row it disproves - the split is by kind of claim, so a policy disagreement (who should be trusted, which risk to accept) is a `QUESTIONS:` item while "the policy asserts this channel is blocked, here is it not being blocked" is a finding. The panel proved this necessary by disproving a claim in the very row that introduced the gate. (b) A finding is CONFIRMED against the code before it is filed, the same bar Step 6 sets for auto-fixing: filtering out-of-scope findings does nothing about wrong ones, and in prisms mode low agreement is expected, so a lone unverified finding is as likely to be a model artifact as a bug. (c) Unresolved `QUESTIONS:` are carried into the summary's "Needs your decision", so a challenge to a project assumption reaches a human instead of dying in the panel. Because the hard rules keep out-of-scope candidates OUT of `FINDINGS:`, the duck output shape carries a dedicated `SCOPED-OUT:` section that consolidation consumes - without it the promised audit trail could never reach the consolidator. Consolidation records such a candidate as `Dismissed-as-out-of-scope` with the rule that makes it so, and explicitly does NOT open a follow-up issue for it. Without this gate a panel manufactures work faster than it can be done: over issues #623-#1073 in this repo the issue branching factor reached 1.83, with 13 spawned issues becoming parents themselves. | `scripts/test_multi_duck.py` - `MultiDuckScopeGateTests.test_the_panel_respects_a_declared_threat_model_and_dismisses_out_of_scope_findings`, `MultiDuckScopeGateTests.test_the_scope_gate_still_admits_the_findings_that_always_matter`, `MultiDuckScopeGateTests.test_an_inaccurate_enforcement_claim_can_never_be_dismissed_as_out_of_scope`, `MultiDuckScopeGateTests.test_findings_are_verified_before_filing_and_questions_are_carried_through`, `MultiDuckScopeGateTests.test_the_scope_policy_is_read_from_the_base_revision_not_the_reviewed_diff`, `MultiDuckScopeGateTests.test_a_dismissed_candidate_actually_reaches_the_consolidator`, `MultiDuckScopeGateTests.test_an_incidental_pre_existing_finding_is_not_filed_as_an_issue` |
| MDUCK-COUNT-13 | The default panel is **4** ducks, not 8. A duck is a whole model context reading the same bundle, so the default is the SMALLEST panel that still keeps the prisms guarantee (2 ducks per aspect, on different model families) and it costs about half of the 8-duck default it replaced; the 1..12 clamp is unchanged, so a large or high-stakes change still asks for a wider panel explicitly. Because an agent reads the skill section by section, EVERY statement of the default has to agree - the front matter, the `count` input, the aspect math (`count=4` -> `A=2`, aspects 1-2), the worked prisms example (which shows the default panel, 4 ducks over 2 aspects), and the Notes - so no section can launch a panel twice the size the next one describes. The narrower aspect coverage is stated as the trade it is, with the two ways to widen it (name the concern in `guidance` so it becomes aspect 1, or raise `count`). | `scripts/test_multi_duck.py` - `MultiDuckPanelBudgetTests.test_the_default_panel_is_four_ducks` |
| MDUCK-EFFORT-14 | An `effort` input selects which TIER of models the panel is drawn from, and the per-duck reasoning-effort floor: exactly two levels, `high` (the flagship roster at a `high` floor, the default) and `medium` (a mid-tier roster at a `medium` floor, materially cheaper and faster). SKILL.md carries BOTH rosters as example tiers, each obeying the same diversity-first rule (front-load one model per family across at least four provider families), and the medium tier never replays the flagships the high tier front-loads - otherwise "medium" would be the default panel under a new name. The tier changes only how deep each reviewer is: the modes, the 2-ducks-per-aspect cross-family pairing, and the hard rules are identical, and a run never MIXES tiers, since a medium duck paired with a flagship is presented as an equal second opinion when it is not. Spending less therefore means lowering the tier or the `count`, never the number of families. | `scripts/test_multi_duck.py` - `MultiDuckPanelBudgetTests.test_effort_selects_one_of_exactly_two_model_tiers` |
